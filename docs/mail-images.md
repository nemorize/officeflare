# 메일 이미지 저장과 캐시

신규 수신 및 EML/MBOX 가져오기는 메시지를 게시하기 전에 서버에서 외부 스타일시트와 이미지, CID 첨부 이미지를 처리합니다. 스타일시트는 정제하여 본문에 포함하고, 이미지는 검증한 바이너리 파일로 R2에 저장합니다. 본문에는 이미지 파일을 읽는 URL이 들어가며 Base64 이미지 데이터를 전송하지 않습니다. 원본 메일과 첨부 파일은 보존합니다.

본문 리비전별 메타데이터는 `bodies/...json.render-v2.json`, 이미지 파일은 `bodies/...json.render-images/<SHA-256>`에 저장합니다. 파일 이름에 이미지 내용의 해시를 사용하므로 같은 이미지를 반복 사용해도 브라우저는 하나의 URL을 재사용합니다. HTML의 data 이미지도 서버에서 R2 파일로 변환합니다.

메일 버킷은 비공개로 유지합니다. 본문에 넣는 URL은 `/api/mail/mailboxes/:mailbox/messages/:message/render/assets/:hash?grant=...` 형태입니다. 해당 메시지 리비전으로 제한된 서명은 10~15분 동안 유효하고 5분 단위로 같은 URL을 발급합니다. 이미지 요청에서 계정·세션·메일함 읽기 권한과 현재 본문 리비전을 확인한 뒤 R2 본문 스트림을 반환합니다. 일반 API 액세스 토큰을 URL로 노출하지 않습니다.

이미지 응답은 `Cache-Control: private, max-age=300, immutable`과 R2 ETag를 반환합니다. `If-None-Match`가 일치하면 인증·인가 확인 후 304를 반환합니다. iframe은 `allow-same-origin`만 허용하여 브라우저 이미지 캐시를 재사용하며, `allow-scripts`와 CSP 스크립트 실행은 허용하지 않습니다. 높이 관찰과 링크 클릭 확인은 부모 화면이 담당합니다. iframe은 이 메시지의 이미지 경로만 로드할 수 있으며 외부 원본 URL과 data/blob 이미지는 차단합니다. 클라이언트에서 이미지별 fetch·Base64 변환·postMessage 삽입은 수행하지 않습니다.

## 본문 표시 순서

UI의 대화·메시지 상세 응답은 본문과 저장된 렌더 결과(`rendering`)를 함께 반환합니다. 서버는 본문과 렌더 메타데이터를 병렬로 읽고, 대화 목록도 병렬 조회합니다. 클라이언트는 상세 응답의 렌더 결과를 캐시에 넣으므로 정상적으로 준비된 메일은 추가 렌더 API 호출 없이 표시합니다.

미처리 메일이나 재시도 대상은 `waitUntil`에서 서버 준비 작업을 실행하고, 조회 응답은 기존 결과 또는 정제된 기본 본문을 즉시 반환합니다. `pending: true` 동안에만 클라이언트가 `render?defer=1` 상태를 1초 간격으로 최대 30회 확인하며, 준비가 끝나면 완성된 HTML로 갱신합니다. 동시 조회는 같은 서버 준비 작업을 공유합니다. 기존 동기 렌더 API는 호환성을 위해 유지합니다.

iframe에는 정제된 HTML을 한 번 쓰고 즉시 높이 관찰을 시작합니다. 이미지가 모두 로딩될 때 발생하는 `load` 이벤트를 기다리지 않으므로, 느린 이미지 때문에 본문이 초기 높이 128px에 잘려 남지 않습니다. 이후 이미지가 도착하면 높이를 다시 계산합니다.

`MAIL_RENDER_ORIGIN`은 서비스의 HTTPS origin으로 설정합니다. 공개 DNS 검증, 리다이렉트 검증, SVG 정제, 이미지당 5 MiB 및 메일당 96개·20 MiB 제한을 유지합니다. 한 메일 처리 중 동일 도메인의 DNS 검증은 공유합니다. 영구 삭제 시 본문 정리 작업에서 이미지 파일과 메타데이터도 삭제합니다.

HEIC/HEIF 이미지는 `MAIL_IMAGES` Cloudflare Images 바인딩으로 서버에서 WebP로 변환한 뒤 R2에 저장합니다. 외부 이미지, CID 첨부 및 HTML data 이미지에 동일하게 적용합니다. 변환 전 4천만 픽셀 제한과 변환 후 5 MiB 제한 및 실제 이미지 포맷을 검사합니다. 일반 PNG/JPEG/GIF/WebP/AVIF/SVG는 기존 검증 경로를 사용합니다. `wrangler.jsonc`의 `images.binding` 설정을 함께 배포해야 하며, 변환은 Cloudflare Images 사용량으로 집계됩니다. 변환 결과는 R2와 서버 리소스 캐시에서 재사용하므로 메일을 다시 열 때마다 변환하지 않습니다. 바인딩과 HEIC 지원은 [Cloudflare Images 문서](https://developers.cloudflare.com/images/optimization/binding/) 및 [지원 형식](https://developers.cloudflare.com/images/get-started/limits/)을 참고하세요.

## 기존 메일 처리

사용자가 본문을 열 때 저장된 v2 결과가 없으면 서버에서 준비합니다. 이전 v1 Base64 저장 결과가 있으면 저장된 바이트를 R2 파일로 옮기고 URL 메타데이터로 전환합니다. 이 과정에서 원본 이미지 서버에 다시 요청하지 않으며 v2 저장이 끝난 뒤 이전 v1 결과를 정리합니다.

아직 준비된 결과가 없는 메일은 첫 본문 조회를 계기로 서버 백그라운드에서 이미지를 내려받아 R2에 저장합니다. 이후 조회에서는 원본 서버에 다시 요청하지 않습니다. 메일 목록 조회는 이미지 처리를 실행하지 않습니다. 별도 마이그레이션 명령이나 API 키 설정도 필요하지 않습니다.

일부 이미지가 실패해도 본문과 정상 이미지는 표시합니다. 기존 실패 기록에 재시도 시간이 없으면 다음 본문 조회에서 실패한 리소스를 자동으로 재처리합니다. 재시도 시간(`retryAfter`)과 횟수(`retryAttempts`)를 저장하며, 반복 실패 시 간격은 1분부터 최대 1시간까지 늘어납니다. 본문의 다시 시도(`retry=1`)는 이 대기시간을 건너뜁니다. 자동·수동 재시도 모두 정상 이미지의 R2 파일을 재사용하며 성공하면 실패 기록과 재시도 시간을 지웁니다. 이미지 처리 실패 시 서버 로그에 메시지 ID, 내부 리소스 경로 및 오류 원인을 남깁니다.
